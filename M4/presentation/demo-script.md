# Demo script: ClaimSense on the deployed system (≤ 10 minutes)

**Purpose:** the brief's "client presentation with a live demonstration" and Submission 2's "demonstration
recording of no more than ten minutes".
**Recorded on:** the deployed system, https://d2jfndltae6j40.cloudfront.net, with real models, the real door,
Cognito and the audit trail. All claims are synthetic.

**How it's produced:**
- a screen capture of the deployed console, driven step by step from this script;
- the narration below, voiced by text-to-speech;
- title cards from the [steering deck](https://claude.ai/artifact/NBH6W3JFGmrekEWPDHqhHU);
- all of it assembled into one MP4 with captions.

Nothing is staged: every screen is the real system answering. Final runtime **9:54**, under the 10-minute limit. Built by `make_demo.py` (tts → record → stills → assemble).

| 6:03–6:25 | Deck slide 5: how it works | Only now, the architecture, in one line. The adjuster works in the console. The agents judge and cite. Everything they read passes through what we call the governed door: plain code that decides who may see which claim, computes dates and amounts, and writes an audit row for every call. The model never decides access or money. |
| 6:25–7:18 | GitHub Actions on main: every job PASS; 150/150 with the model required; all six adversarial families incl. prompt injection 14/14, cross-record leakage 10/10, forced auto-decision 10/10; Promptfoo 150/150 + 7/7 | How do we know it still works after every change? This is the continuous integration run on the main branch. Every merge runs all one hundred and fifty test claims against the live models, inside the exact image that would be shipped. Forty-five of them are attacks, in six families, including fourteen prompt injections, ten attempts at cross-record leakage, where a document asks for another customer's claim, and ten attempts to force an automatic decision, such as pay now, no review needed. All forty-five pass. The rule is strict: at least ninety percent correct, every case decided by the model, and zero adversarial failures, so a single failed attack blocks the release. A second, independent grader, Promptfoo, must agree on all one hundred and fifty cases. Only then is the image pushed. |

## Recording checklist
1. **Warm up:** `python M4/ops/door_smoke.py` → 5/5 PASS, then one throwaway run of CLM-2024-1800, so no first-call
   cold start is filmed.
2. **Before filming:** check that CLM-2024-1800 has no pending draft, so the confirm step shows cleanly (or use a
   fresh run).
3. **Browser:** a 1280×720 window (fits a laptop screen; upscaled to 1080p at assembly), nothing else open.
4. **Sign-in:** each user's own password is typed by the person recording, never by a script; the password field shows dots and the typing is cut.
5. **Captions:** generated from the narration column.

## Backup plan (for a live session, and if a take goes wrong)
| If… | Do this | Why it's safe |
|---|---|---|
| the console won't load or a run errors | switch to the recorded video (same system, same claims) and **say so**; never debug live | the recording is the same deployed system |
| the door is down ("Claim systems unavailable") | run `python M4/ops/door_smoke.py`; if it fails, show `incident-drill-2.txt` and the dashboard: recovering from this is the point of slide 4 | the outage label itself shows fail-closed behaviour |
| sign-in fails | check the username and password (a lockout clears after a minute); else show the recording | — |
| the model provider is slow | narrate over the streaming agents; p95 is 13 s, so wait up to 45 s before switching to the recording | — |
| an answer differs from the script | show it, say what you expected, check it against its eval case afterwards; never edit the narration to match | honesty is the deck's whole case |
| asked for a number not on screen | "I’ll send that in writing." Never estimate on the spot | — |
| running long | skip the terminal audit step (5:25) and the CI step (6:05); go to the dashboard and the ask | the rest still covers all five acceptance areas |
