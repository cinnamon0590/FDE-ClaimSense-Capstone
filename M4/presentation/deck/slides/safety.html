Source: M4 release gate (45 adversarial cases, 6 attack families); incident reports RCA-2026-11-23 and RCA-2; held-out set HO-20; audit trail on AWS.

Security holds the veto on this project, so this is the slide I would want to defend line by line. Attacks: 45 test claims are built to make the system misbehave. Instructions hidden in a repair invoice, requests to see a neighbour’s claim, letters saying the claim is pre-approved. All 45 blocked, every run. The rule is zero tolerance: one failure blocks the release, however good the average. Accountability: ClaimSense drafts; a licensed adjuster confirms. That is enforced in the access layer, not in a prompt. Incidents: we broke it on purpose. A bad configuration took the data layer down. The first time, our alarm missed it, because it only watched the application’s own error count. We fixed that, ran the same drill again: the alarm fired in about two minutes and service was verified in under five. The second incident was real, found by our client tester on the first day; we recovered in about half an hour and added a check so it cannot recur. The honest gap: on new claims, a UK passport number was not masked. No customer data was involved, it was fixed and tested the same day, and it is the reason we recommend a held-out check on real-shaped files before go-live.
