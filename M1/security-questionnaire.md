# Vendor security questionnaire: ClaimSense AI answers for AutoSure Insurance

**Added Features / Extra Credit artifact** (the Week 14 class centrepiece). Every answer names the **control**,
**where it lives** (code, integration layer or system of record, never the model), and the
**proof** a reviewer can re-run. "We'll figure it out during the build" appears nowhere.

| # | Domain | Answer: control · where it lives · proof |
|---|---|---|
| 1 | Data residency & segregation | All pilot data and processing run in AutoSure's dedicated AWS account in **us-east-1**: S3, DynamoDB, ECS, OpenSearch. Nothing is shared with other clients; resources are tagged `Project=ClaimSense, Client=AutoSure`. Model inference goes to the OpenAI API (see #14) with PII-masked inputs only. **Proof:** `7-cloud/evidence/`. |
| 2 | Data classification & minimisation | Fields used are only those in the typed contracts (`additionalProperties: false`). Every one is justified in `6-synthetic-data/data-shapes.md`. The claimant name is the only PII-class field; it is masked before prompts and logs. **Proof:** schemas + `validate_data.py`. |
| 3 | Synthetic vs. production data | **Built, tested and demonstrated entirely on synthetic data** (brief constraint #3). The fixtures are generated from the eval cases and every file is marked `synthetic: true`. Nothing breaks without real data. What we can't measure until Phase 2 is real-world confirmation rate, which is why that's priced separately. |
| 4 | Identity & agent authorization | Agents act **on behalf of the signed-in adjuster**: the Cognito JWT travels with every call and the boundary derives identity from the token, never from the request. Agents hold **no standing credential** to any system. An adjuster scoped to their queue can't pull another claim through the agent. **Proof:** contract test `unentitled_user_gets_no_claim_data`; M3 two-user test. |
| 5 | Access control & least privilege | Role-based access via Cognito groups → claim scope, **enforced in the data boundary in code before any agent runs**, not in a prompt. Lambda/ECS roles get only the actions they use. **Proof:** `reference_boundary.entitled()`; eval CS-019; the M3 two-user test with both responses and audit rows. |
| 6 | Authentication & secrets management | Users: Cognito (OIDC, MFA). Services: IAM roles; CI uses GitHub OIDC (no long-lived AWS keys). The OpenAI key lives in **AWS Secrets Manager**, read at runtime, rotated, never in git, code, logs or prompts. The repo's `.gitignore` excludes `.env`, and we scan for secrets before every push. |
| 7 | Encryption | In transit: TLS 1.2+ everywhere. At rest **today**: S3 SSE-S3 (AES-256), DynamoDB, ECR and Secrets Manager encrypted by default with AWS-managed keys (verified in `7-cloud/evidence/`). **For production**: customer-managed KMS keys in AutoSure's account, so AutoSure holds the keys and can revoke them, and our access, unilaterally. Removing our IAM roles also invalidates every token we hold. |
| 8 | Audit logging & traceability | Every boundary call (read, write, allow, **deny**, replay, error) writes an **append-only** audit record `{ts, request_id, user_id, groups, on_behalf_of_agent, action, resource, decision, reason}` to DynamoDB, streamed to CloudWatch. IAM denies update/delete on the audit table. Exportable on request. **Proof:** contract test `every_call_is_audited`. |
| 9 | Prompt injection & untrusted content | Claim narratives and documents are marked `untrusted`, scanned for injection, and **wrapped as data** before reaching a model. Retrieved chunks failing the provenance manifest are **quarantined**. The boundary limits what any call can return, so an injected "fetch another claim" dies at the entitlement check. **Proof:** CS-016, CS-017, CS-020 at 100% in the gate. |
| 10 | Model & output governance | Coverage statements must cite a clause **actually retrieved** (checked in code). Dates and money are computed by code and overwrite the model's fields. Low-confidence or guardrail-hit cases go to `flag_review`. **Proof:** CS-003 / CS-014 (stale status fields both ways), CS-020 (poisoned clause). |
| 11 | Human-in-the-loop & autonomy limits | The co-pilot **recommends only**: every recommendation is a draft. Confirmation is a **separate human-only write**; agent identities are refused, an override needs a reason, and > $25K needs a senior adjuster. The boundary is configured in the data boundary's code, and changes need a reviewed PR plus a green eval gate. **Proof:** `agent_identity_cannot_confirm`, CS-018. |
| 12 | Vulnerability management & SDLC | PR-based changes; CI runs the eval suite and **blocks the image push** when it fails; ECR scans images on push; dependencies pinned and scanned. Patch SLA: critical 7 days, high 30 days. |
| 13 | Incident response & breach notification | Runbook with detection (CloudWatch alarm), containment (writes-off switch, rollback to last green image), RCA within 5 business days, and a new eval case for every incident. **Contractual breach notification within 24 hours.** Named 2 am contact: the FDE on-call (Susan Wellington), then the vendor security lead. |
| 14 | Subprocessors & model providers | **OpenAI** (model inference; enterprise API terms: inputs not used for training, zero-data-retention requested); **AWS** (hosting, storage, search, identity); **GitHub** (source and CI; synthetic data only). No other processor sees claim data. Listed in the SoW data annex. |
| 15 | Exit, data deletion & IP | AutoSure owns all its data and everything derived from it: embeddings, eval labels, prompts tuned on its data. On exit: S3, DynamoDB, the OpenSearch index and secrets are deleted by the scripted teardown, with **deletion verified by a resource inventory report**; our IAM access is removed. IP split per SoW §7. |
